二、失败的精确位置与根因（代码级，不是猜测）

  崩点（四腿完全一致）：
    File "datautils.py", line 118, in get_c4
      i = random.randint(0, tmp.input_ids.shape[1] - seqlen - 1)
    ValueError: empty range for randrange() (0, 0, 0)

  上下文（datautils.py:112-120）：
    112  for _ in range(256):
    113      while True:
    114          i = random.randint(0, len(valdata) - 1)
    115          tmp = tokenizer(valdata[i]['text'], return_tensors='pt')
    116          if tmp.input_ids.shape[1] >= seqlen:      # <-- 应保证 > seqlen
    117              break
    118      i = random.randint(0, tmp.input_ids.shape[1] - seqlen - 1)

  当某条 c4-validation 样本 tokenize 后长度**恰好等于 seqlen**（8192）：
    - 第 116 行 `>= seqlen` 判定通过、break；
    - 第 118 行上界 = 8192-8192-1 = -1 → randint(0,-1) → empty range。
  random.seed(0) 固定，四腿抽取序列相同，因此必然踩同一条样本。

  为什么 7B 没踩：
    main.py:100 缓存名 = f'{cache_dir}/testloader_{model_family}_{dataset}_all.cache'，
    model_family = net.split('-')[0] = "Llama"（Llama-3 与 Llama-2 相同）。
    7B 有预生成的 ./cache/testloader_Llama_c4_all.cache，直接 torch.load，不进 get_c4。
    8B 按本轮硬约束用独立 ./cache_llama3_8b（防 128K/32K 词表碰撞），该目录无 c4 缓存
    → 必须现场 get_c4 生成 → 触发 bug。

  ⚠ 注意：不能把 7B 的 testloader_Llama_c4_all.cache 拷给 8B——那份是 32K 词表算的
  token id，8B 是 128K 词表，喂进去会得到完全错误（但不会报错）的假 PPL。

三、我们建议的修法（两选一，请开发组确认；本轮未擅自改代码）

  方案 A（最小、不改变随机流，推荐）：
    datautils.py:118
      i = random.randint(0, tmp.input_ids.shape[1] - seqlen - 1)
    →
      i = random.randint(0, max(0, tmp.input_ids.shape[1] - seqlen - 1))
    语义：样本恰好等于 seqlen 时只能取整段 i=0；不重抽、不消耗额外随机数，
    对任何已有 7B 结果零影响。

  方案 B（改循环条件，会重抽样本）：
    datautils.py:116  `>= seqlen` → `> seqlen`
    保证进入 118 行时上界 >= 0，但会改变 valenc 的样本选择与随机流。
    诊断已确认 c4 中存在 >8192 的样本（前 300 条里有 1 条），故不会死循环；
    但会改变抽样序列 → c4 PPL 与"不修"的口径不同（8B 无历史值，可接受）。

  ⚠ 推荐方案 A：不依赖样本分布、不改变随机流、语义最直接（恰好等于 seqlen 时整段取 i=0）。

  另：本轮所有 8B 腿共用 ./cache_llama3_8b；一旦 c4 testloader 生成成功会被
  torch.save 缓存（main.py:111），后续三腿直接复用 → 修好后 fp16 腿先跑通即可
  验证缓存落盘，再跑其余三腿。

六、诊断结论（deploy_review/r13_c4_diag2.py，只读，输出 r13_c4_diag.txt）

  valdata 条数 = 45576；vocab = 128000
  用 8B tokenizer + random.seed(0) 按 get_c4 的 valenc 逻辑跑 256 轮：
    crash_at = None          ← 本次复现**没有崩**
    前 300 条长度分布: {'<8192': 299, '==8192': 0, '>8192': 1}

  如何理解这个"没复现"：
    - 崩溃机制本身没有疑问：traceback 的 `empty range for randrange() (0, 0, 0)`
      等价于上界 -1，即 shape[1] == seqlen，这是确定性的数学关系。
    - 但用 seed(0) 在诊断环境里抽的 256 个 index 恰好都没落在 ==8192 的样本上，
      说明那条样本位于更靠后的 index，或实际运行的 valdata 加载顺序与诊断略有差异
      （arrow 缓存命中路径不同）。因此"具体是哪一条样本"未能定位。
    - **重要副产品**：前 300 条里确实存在 1 条 >8192 的样本 → 方案 B（`>=` → `>`）
      不会死循环。但方案 B 会重抽、改变随机流；方案 A 不会。仍推荐方案 A。

  结论：根因确定（off-by-one 边界），修法确定（方案 A 最优），仅"具体样本 index"未定位，
        不影响修复。
